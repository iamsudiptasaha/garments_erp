# Dyeing edition groups — approved implementation on dev

Migrations: `20261124150636_fabric_er_remediation.sql` (approved local remediation), `20261123200917_lab_dip_edition_groups.sql` `20261123210053_fabric_requirement_integrity_boundary.sql`, and `20261123213100_scope_fabric_constraint_validation.sql`. This change has not been applied to hosted Supabase. No production deployment is authorized.

## Ownership and persistence

Brand-specific colour → Lab Dip edition/mixture → approval versions. `item_part_fabric.lab_dip_id` selects the edition. Approval never filters eligibility. `variant_item.id` still resolves style, shared variant and production part; its historical lab column is retained for compatibility but removed from the live writable contract and item editor. The requirement status view is `view_item_part_fabric_labdip_status`, keyed by `item_part_fabric_id`, not variant identity. Fractional consumption remains unchanged despite the diagram's integer annotation.

Program → `dyeing_program_lab_dip` → fabric items → composite M:N planner links. Each group explicitly owns edition/version and optional historical `batch_no_lab_dip_version_map.id`. Composite FKs enforce version membership and item/program ownership. Program+edition is unique; a shared transaction lock and deferred guard enforce six edition groups, including concurrent writes and replacement of a group within a transaction. Different editions of the same colour remain separate. Program items retain their program ID as an FK-checked ownership reference.

Previous batches must have the same edition, may have another version, and cannot originate from any item of the current program. Output batch mappings retain their original exact version. Immediate database guards freeze receipt identity/owning bill/origin, group edition/version, originating item ownership/fabric and output-map identity from first recording. Coordinated edits, reassignment, deletion and batch renaming cannot rewrite provenance. Colour mappings referenced by editions cannot change their colour/brand foreign keys. Ordinary colour display-label edits remain separate. Costing, automatic receipt identity/quantity, stock, coverage and production calculations are reused unchanged.

“Approved from Previous Program” is a reuse description, not another approval state. The group explicitly records `source_dyeing_program_id` when the operator reuses an edition from another program. The source must contain the exact edition; self-reference and cycles are rejected. No chronological restriction is imposed. Existing rows retain NULL sources because historical intent cannot be inferred. The original program is not relabelled merely because another program references its edition. The edition ID is reused and its version remains explicitly selected. No edition, approval review or previous-batch selection is generated. The migration only renames a matching persisted label, preserving its ID and references; it inserts no new status. The audited live lookup had no matching persisted label.

## Atomic contract

The existing public `erp_save_fabric_document` and private core save header, groups, items and links together. Groups precede items; deletes run in reverse. Composite links are handled explicitly through their two actual keys, never a synthetic database ID. Existing links reopen selected; addition reviews retain the complete set and recalculate only affected ordered quantities from authoritative SQL requirement kg. Manual overrides afterward are preserved. If several existing rows share one edition/fabric pair, Add from Planner requires the operator to choose Manage Links on the intended row; it never guesses or merges those identities. Unlinking preserves the item's quantity and other rows. Removals are explicit and included in review.

Link mutations require program create/edit plus Production Items view; existing one-link Planner permissions remain unchanged. The private group table has RLS and no browser grants. Catalogue mappings inherit the existing program-item read permissions. Snapshots serialize all bigint references as strings. Group/item and link-set digests in `fabric_json` invalidate stale complete-document reviews even for link-only writes where the timestamp trigger correctly treats a header-only stamp as a no-op. The reviewed SQL total also rejects stale planner quantities. Requirement and one-link RPCs explicitly complete their named integrity checks inside their existing authorized boundaries before returning to the authenticated caller, then restore deferred traceability. Document saves defer the complete graph at entry and validate at exit, preserving receipt/batch atomicity even after another command in the same transaction. No private-table SELECT grant or SECURITY DEFINER trigger is introduced. Existing row/root optimistic checks, audit logging and dyed-bill attestation remain active.

Planner saves await the existing workspace refresh before closing, so the next program editor receives current link/group revisions rather than the previous cached Fabric snapshot.

Frontend sources: `program-editor.js` owns the document form; `program-model.js` stages group/item/link changes; `relationships.js` resolves persisted group ownership. The generic BillEditor program form was retired. `FabricRequirementFields`, shared selectors, Overview controls, preference store, native dialogs and `FabricSheet` remain shared. Only ordered kg opts into staged worksheet entry; all other cells and other worksheets remain protected.

## Release and recovery

Preflight locks source tables and fails on orphan/dyer/batch inconsistency, multiple versions/batches within a proposed group (including NULL disagreement), or more than six editions. Backfill preserves existing program/item/requirement/link/output-batch IDs. New constraints and guards validate the complete graph before old columns/view are retired. Any error rolls back the migration transaction. Conflicts require explicit reconciliation; no arbitrary “first/latest” choice is made.

For future approved release, apply this migration and its matching portal through reviewed GitHub Actions release gates in a maintenance window. The old portal cannot write the new item contract; do not serve mismatched releases. Keep a verified pre-release backup and original commit. Before new writes, transaction failure leaves the old schema intact. After successful migration, recover with a reviewed forward fix or coordinated backup restore through the deployment recovery process; do not blindly revert the portal after cross-version historical-batch selections exist. No hosted SQL/CLI application is permitted.

Tests cover empty replay, populated backfill/conflict rollback, version/edition integrity, six-group and uniqueness races, same-edition/different-version batches, own-program rejection, receipt protection, exact component identity, complete links, stale reviews/totals, atomic rollback, manual overrides, permissions, costing/stock regressions and Chromium document interactions. Component browser fixtures use synthetic transport; the authenticated acceptance runner additionally exercises the actual ProgramEditor, Supabase RPCs, PostgreSQL persistence and UI reload. Database tests exercise independent transactions and two-session races. Neither establishes a production rollout.

## Approved remediation and release boundary

All remediation is local on `dev`; no push or hosted migration is authorized. The new migration adds one nullable source-program reference with an exact-edition composite FK and index, immutable provenance guards, a shared SQL linked-required-kg function, deferred Final-document validation and minimum-width program number formatting. Existing IDs, numbers, costing, stock and coverage calculations are preserved. Non-Draft documents with empty/no groups fail preflight and require explicit reconciliation; valid Draft empty groups remain allowed.

The standalone planner RPC now requires the reviewed program and requirement revisions plus final linked-required kg. Its old four-argument signature is retired rather than retaining an unguarded write path. Both supported paths use the existing authoritative requirements view through `fabric_linked_required_kg`. An actual addition recalculates the complete set; removal leaves ordered kg unchanged. A subsequent explicit manual quantity remains valid. Reconciliation refreshes the final-set validation total even when a staged addition is later removed. Standalone activity records actual transitions once; full program saves retain one event with reviewed changes and resolved identities. No-op linking is not logged as a mutation.

Only Draft can retain empty edition groups; historical Unclassified documents are not silently normalized. Final requires at least one group and a fabric item in every group; deferred checks allow atomic header/group/item intermediate states. Requirement eligibility remains exact edition and fabric, irrespective of approval. Previous batches retain same-edition/any-version eligibility, exclude current outputs and have no date restriction.

The confirmed review now includes the union of old/new groups, rows and links, with old/new edition/version/batch/source and destructive quantity context. Local preview selectors and writes no longer assign an edition to `variant_item`; the two approved removal-only files have explicit reviewed ownership fingerprints while unrelated prototype code stays frozen.

Validation is scoped to affected programs for program/group/item operations; group link validation is scoped to the affected group. Custom query plans avoid generic optional-filter plans. Other ownership changes retain whole-graph validation. Global advisory locking remains deliberately intact because source balances and cross-document paths share it; no unsupported claim of parallel-program throughput is made. Two-session tests cover sixth/seventh groups, duplicate editions, recording versus version changes and stale planner link writers.

There is no routine correction bypass or client-settable override. A genuine historical correction requires separate explicit authorization, reviewed forward SQL through the existing GitHub Actions release process, an audit record containing actor/reason/before/after identities and provenance/stock/cost regression verification. Restoring the old portal after this migration is unsafe because the link RPC signature and source contract change; release matching database and portal together. Recovery is a reviewed forward fix or coordinated verified backup restore.

Actual migrated-object assertions live in `database/tests/fabric-er-schema.sql`; the projected coherence checker is an additional fast check, not a substitute for PostgreSQL verification. `fabric-er-remediation.sql` and `fabric-er-concurrency.mjs` protect the confirmed defects; populated backfill verifies identity preservation and that no source relationship is invented. Authenticated acceptance covers multi-edition creation, explicit unapproved versions, batch/source selection, complete link sets, manual overrides, removals, reload, stale review, Finalization, permissions and receipt-provenance rejection.

The integration pass also exposed a pre-existing serialization assumption: unrelated Lab Dip saves required every existing version to have an approval-history row. `versionWrite` now preserves NULL review fields for unchanged unreviewed versions; it does not synthesize approval history. Empty Draft documents remain discoverable in the normal Overview and Sheet with their real header identity, zero fabric items and a presentation-only empty-row key. No fictitious fabric item is created.
