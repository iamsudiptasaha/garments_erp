# ER review — 29 October 2026

Read-only comparison of the saved `/Users/user/Documents/Garments/Flowcharts/Fabric.drawio` first four sheets (fabric, item, billing, misc) with current garments_erp columns, constraints, foreign keys and non-timestamp triggers. No database/UI changes made in this review. Diagram changes are proposals until migrated; the local sample UI is a third representation that must subsequently follow the reconciled schema.

## Production blockers

1. **Moving a job loses stage identity if implemented as an UPDATE of job.stage_id.** job owns a single stage, dates, verifier and stage-coded job_code. stage_pieces belongs through design_per_job to that same job. There is no predecessor/source-stage link. Preserve an execution per stage/attempt, or introduce job_stage_run beneath a stable task. Link the next execution to its explicit source. Do not infer provenance solely from stage.sort_order: skipped stages, redo and multiple jobs make that ambiguous. The Kanban card can present the current execution without erasing earlier executions.
2. **Job variant link is internally contradictory in the diagram.** design_per_job lists variant_item_id and unique(job_id,variant_item_id), but its connector still ends on variant. The database still has design_id -> variant(id). Choose variant_item as the production counting identity, then require it to belong to the job's item_part. Rename the table to job_variant_item (or another agreed consistent name), not just a misleading FK column.
3. **Challan counting is still at the old identity.** challan_job_item_pieces retains design_id -> variant in the database/diagram while job counting now proposes variant_item. Link challan quantities to the same job-variant-part identity as stage quantities. An FK alone must not allow a different item/part's variant or size.
4. **PP and stock fields are not migrated.** Diagram adds stage.pp_stage and replaces stage_pieces.pieces_received with pieces_stock_in/pieces_stock_out. Database still has no pp_stage and only pieces_received. There are no stock-in/out handoff functions. Require PP stages not to track production pieces; define the relationship with track_pieces for non-PP stages that also do not count pieces. Do not treat renaming pieces_received as both input and output.
5. **Cutting quantity allocation is unresolved for multiple variants.** item_cut_ratio is one quantity per item_size_list; stage quantities are per variant-item and size. Copying the total into every variant can multiply the production plan. Decide whether item_cut_ratio is a per-variant count, an overall item count split by explicit allocations, or a ratio combined with another total. variant.share_weight is not currently an allocation rule.
6. **Verification is a stored FK, not an enforced workflow.** job.verify_employee_id is nullable and only references employee(id); no handoff/update command validates an employee on every change. A verified operation should atomically record verifier/time, source execution, input snapshot and output changes. Both authenticated and direct-link routes must call that same command. Cancelled verification must leave the board/data unchanged. Simply entering a known employee code does not establish identity without the agreed validation mechanism.
7. **Repeated challans can double-issue the same stock.** Many challan_job_item rows may refer to one job, so repeatedly copying the entire stock-in amount is unsafe. Use stock-in as the initial suggestion, bounded by the unissued balance, and verify before committing. Output/completed quantities and challan outbound quantities are different measures.
8. **Retry/snapshot semantics are not represented.** A redo needs a distinct execution/attempt; predecessor edits must not silently rewrite input already accepted by a later stage. Define completed-zero versus not-yet-entered explicitly even if output is initially zero. Reject duplicate handoff submissions through idempotency/unique provenance.
9. **Quantity constraints are missing server-side.** Production piece columns are numeric without non-negative whole-piece checks; output/input relationships and cumulative challan bounds are not enforced. A stock-in copy must match item, variant-part and size. Larger/smaller output policies (rework, rejects, adjustment) require explicit allowed paths rather than arbitrary edits.
10. **Item production checklist exists but is not wired correctly.** Database already has production_checklist.item_id UNIQUE -> item. It is optional from the item side, not auto-created. Diagram arrows point its four statuses at item_status_list; actual FKs point at lab_dip_version_status (the renamed legacy shared table). Those are different semantics. Choose checklist status vocabulary separately and connect it in item creation/details. The earlier lab-dip migration preserved these old FKs; they were not a validated checklist design.
11. **New job_assignees is absent live.** Diagram adds job_id + assigned_employees_id. Use singular employee_id, FK employee(id), and unique(job_id,employee_id). Define whether multiple assignees have equal edit/verify rights; assignment and verification are separate.

## Item, inventory and billing integrity

12. **Item-part duplicate mapping is allowed.** No unique(item_id,part_list_id) exists in the database; duplicate parts can split counts and make previous-stage matching ambiguous. Item size mapping and cut quantity already have their expected unique keys.
13. **Finished-stock variation is not tied to its production variant.** item_produced links an item and item_in_store; item_produced_pieces links sizes, but not a variant or item_in_store_variation. item_sold has no explicit allocated quantity. Decide how partial sales and multiple finished variants consume production stock; existing links alone cannot prove which variant or how many pieces were consumed from each source.
14. **sellable_unit FK label/edge is wrong.** Diagram points item_size_list_id at item_produced_pieces.item_size_list_id. That column is not globally unique there and cannot be the single-column FK target. Actual DB correctly references item_size_list(id). Use that master FK, or reference the produced-piece row by its ID if provenance is intended.
15. **view_item_in_stock is a physical table.** Despite its name, the database relation has a primary key, FKs and updated_at. Stored derived balance rows can drift unless maintained transactionally. Decide whether this is a true calculation view or an explicitly maintained stock ledger. Diagram returning_item_id differs from actual return_bill_item_id; diagram item_in_store_variation lacks the _id suffix.
16. **PO/billing/size links can disagree.** po_item and billing_item can independently select an item_in_store_variation; their size rows reference any item_size_list. Individual FKs do not enforce matching item/variation/size or correct PO allocation. Add transaction/composite integrity rules after deciding the finished-stock model.
17. **Carton contents cannot express packing quantities.** carton_item links billing_item but has no size/quantity contents. For size-wise cartons/packing lists, a content detail mapping is missing. Its billing_item must also belong to packing_list.billing_id.
18. **Transport docket cardinality needs confirmation.** transport_item has UNIQUE(docket_number) and one carton_item_id, so a shared transport docket cannot span several carton rows under that design. If several cartons travel on one docket, model docket/shipment header -> carton mappings. transport_docket.transport_number_id actually references transport_bill(id): name it accordingly if retaining the relation.
19. **Raw-material receipt FK is out of sync.** Diagram has raw_material_purchase_order_item_id; DB has purchase_order_id -> PO header. Item/price selection needs the PO line relation and a check that material/supplier match that line. Diagram inward_date/billed_quantity/billed_price differ from DB date/quantity/price. The existing XOR check correctly requires exactly one fabric or raw-material source; preserve it. Supplier is nullable live, consistent with the fabric path.
20. **Other cardinalities need business confirmation, not automatic changes.** UNIQUE(packing_list.billing_id) permits one packing list per invoice. UNIQUE(job_worker_bill_items.challan_job_item_id) permits one bill allocation per challan line. These may be intentional, but block split packing/partial billing if those are required. contact_extra's diagram marks key globally unique, while DB has no uniqueness; usually unique(contact_id,key) is the intended scope.

## Fabric and naming drift

21. **Recent lab-dip/batch structure is present live.** Batch numbers are unique; multiple batches may reuse one version. The exact-version consistency triggers and edition closure are in place. No change required to those agreed rules from this review.
22. **Colour/swatch remains duplicated as a legacy column.** Diagram removes color_map.attached_swatch; live database still retains it while lab_dip_version.attached_swatch now owns the approval-reference meaning. The UI no longer exposes the old field. Migrate/remove it deliberately rather than maintaining two meanings.
23. **Fabric diagram omits current yarn_count.** Live yarn_type.yarn_count is required by the agreed derived fabric-name view but absent from that drawing. fabric_name is correctly a derived view field, not a physical knitting_bill_item column. Older comments still describe lab_dip where the FK is lab_dip_version_id. Diagram dyed_fabric_bill.verified_by_employee_id is absent live.
24. **Unify FK naming.** purchase_order_number_id actually refers to yarn_purchase_order.id; use yarn_purchase_order_id. job.verify_employee_id and other verified_by_employee_id names should agree. Diagram job_worker_bill.bill_attacment is a typo (live bill_attachment). employee_emergency FK naming is reversed between diagram and DB. Employee code diagram says SCE-XXXXX; actual agreed format is SCE/XXXXX. supporting_document_*_title are text, not FK columns. attachments.file_size is text; numeric byte count is preferable. Currency, weight and piece units should be explicit.
25. **Natural keys and count checks are uneven.** item.style_code is nullable/non-unique live despite being the QR/manual lookup identity. Decide its uniqueness scope. Enforce non-negative quantities/rates and whole-piece counts selectively; kilogram quantities remain decimal. Bill invoice-number uniqueness should be supplier-scoped if required, not blindly global.
