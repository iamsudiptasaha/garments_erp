# Employee email authentication

HR continues to register employees through the existing linked Contacts workflow. An email is required only when an Administrator invites an employee to use ERP. The existing Administrator designation, role assignments and Auth UUIDs remain in use.

## Account flow

1. In Administration, select an employee, enter their login email, select roles and send the invitation. The account service verifies the Administrator's AAL2 session and uses the native Supabase invitation.
2. The employee opens the invitation link and chooses Continue, sets a password, then signs in with email and password to enroll a TOTP authenticator. ERP authorization requires password authentication, a verified factor and a live AAL2 session.
3. Forgot password uses native Supabase recovery addressed to the registered email. An employee with an existing factor verifies it before choosing a new password. Recovery retains the factor and the linked employee and roles. Disabled ERP accounts cannot write a new password.
4. User Access shows the pending invitation as Needs attention if the ERP link could not be completed. Retry provisioning uses the original employee, email, roles and Auth identity. Once Auth created the identity, retries only complete the ERP link. An unlinked Auth identity has no ERP permissions. If the original message did not arrive or expired, use Resend after the link is complete. If the employee already accepted the invitation, use Forgot password to finish setup.
5. Link existing account is reserved for pre-existing Auth identities with an email and no employee link or invitation reservation. The link starts disabled. Administrators can inspect details, edit roles, disable access or restore an active employee. Changes and invitation requests appear in Activity log.

The native invite call and ERP linking are separate operations. If no Auth identity was created, Retry provisioning can send after the one-minute cooldown. An archived reserved role, a conflicting external Auth identity, or an inactive employee requires resolving that condition before retry. For an incomplete reservation, open View details to cancel it or correct its email. Correction preserves the reserved roles and replaces the invitation. If the replacement cannot finish, use Retry provisioning on the corrected address. Both actions record the Administrator, employee, address change and time. A cancelled native Auth identity can still exist and its address remains occupied in Auth. It cannot be linked to any ERP employee, even if the recipient opens an earlier message.

## Review before release

- Configure Auth with the verified ERP HTTPS origin as Site URL and the exact `/access.html` callback allowed where a redirect override is used, public signups disabled, the phone provider disabled, the email provider enabled and a minimum password length of 12. Install the [invitation](../supabase/templates/employee-invite.html) and [recovery](../supabase/templates/employee-recovery.html) templates. The fragment holds the token hash until the browser strips it and the employee explicitly submits it to Supabase.
- Use a verified custom SMTP account directly with Supabase Auth. The existing HTTP Worker uses a fixed Admin recipient. Its earlier Gmail SMTP acceptance applies only to that Worker. The existing Gmail sender can be reused directly if Google permits an app password for it and it can support delivery volume. Provision a Supabase-specific app password through the credential owner, configure authenticated Gmail SMTP with TLS, and verify sender authorization, link tracking and quota. The Worker secret is separate and cannot establish the hosted Auth settings. Smoke-test invitation, recovery and email-change delivery to controlled inboxes in staging. Keep credentials in the approved secrets store. See [Supabase SMTP guidance](https://supabase.com/docs/guides/auth/auth-smtp).
- Verify that enabled employee identities have confirmed email addresses and review disabled accounts before restoring them.
- Release order is Auth email configuration and the reviewed SQL migration set, then the matching `erp-accounts` Edge Function, then the portal. Use a coordinated cutover because the migrations retire the old recovery RPCs during the same release. The protected Worker release on main and the manually dispatched Pages workflow both check the matching database manifest, deploy the reviewed Edge function, and verify that it rejects anonymous requests before releasing the portal.
- Scope the Actions deployment token to the authorized release identity. The Edge deploy job needs `SUPABASE_ACCESS_TOKEN` and the environment variable `SUPABASE_PROJECT_REF`, matching `VITE_SUPABASE_URL`. Set `APPLIED_DATABASE_MANIFEST_SHA256` separately for each target after its migrations are applied. The production release retains the independent reviewer and branch protection gate. The existing SQL job uses `PRODUCTION_DATABASE_URL`. The function uses Supabase's injected `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` and independently validates the caller and Admin AAL2. Preserve the current gateway JWT setting for this cutover unless it is changed and tested separately. Gmail SMTP credentials belong in hosted Auth configuration. The new account function does not use the legacy Worker recovery secrets.
- Run staging SMTP and functional smoke tests before production with separate project and portal targets. Verify invite and recovery links land at `/access.html` on the intended HTTPS origin and email-change messages contain six-digit codes. Check actual hosted configuration and delivery before claiming readiness.
- Install the [email-change template](../supabase/templates/employee-email-change.html), configure new-address-only confirmation and set a six-digit email OTP with 900-second expiry. Enable the email-address-changed security notification to notify the former address.
- My Profile displays the sign-in email as read-only. Each employee has a distinct primary Contact. Before the profile migration, check for duplicate primary Employee Contact links and have HR correct any duplicates using existing Contacts and Employee workflows.
- Employee registration links the existing contact and still accepts a record with no email. Contact-item email fields are optional. Existing addresses are populated on successful email change.

## My Profile

Account Settings opens My Profile. A password and verified TOTP session allows the employee to update their own Contact name and primary phone, or attach and remove their photo. An empty phone unsets the primary flag and preserves the Contact item. These changes leave sign-in and roles intact. Photos use the existing private employee upload route and retained attachment history. Keep that route enabled and its bucket private.
